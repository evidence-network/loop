Daily evidence reports

Once a day, one node on the mesh, the reporter, asks every node on the commitment list the same two questions and saves exactly what came back. This page shows those saved answers, one row per node per day, with a link to every raw file. It is built from the saved files and nothing else.

New here? Read what the reporter asks and what each result means first. Then the reports.

What the reporter asks

Each node on this network keeps a book of sealed records about the exchanges it takes part in, and answers evidence requests under its own disclosure policy. Most records are answered only to the other party of that exchange. Two questions are answered to anyone, and they are the only two the reporter asks:

  • checkpoints: the node's signed checkpoints. Each one commits to the size and root of the node's log at that moment. It shows the book exists and keeps growing, without showing any record in it.
  • history_card/1: a signed card derived from the node's whole history: its checkpoints, each with the proof that it extends the one before. Again, no record's contents.

The reporter asks over the mesh, addressed by node id, and signs every request with its own published key, so each node can see who asked. It asks nothing else, and it never asks itself.

What each result means

Each question gets exactly one result per node per day.

verified
The node answered, and the reporter's own node checked the answer's signature under the key the node's host announces on the mesh, and the answer's form. It means: this node, holding that key, signed this answer to this request. It does not mean the node's records are true or complete, that the node is trustworthy, or that anyone vouches for it. Repeating this check yourself, offline, is not possible yet; see checking an answer yourself. The key column also says whether the announced key is the one the node listed (listed_key=match) or not (listed_key=differs). "Log size at checkpoint" is the size of the node's log (mmr_size) and the time in the checkpoint the answer is anchored at, as the answer states them. A size that grows from day to day shows the log keeps growing.
no_checkpoint_yet
The node signed a coverage_unsatisfiable answer: it has not cut its first checkpoint yet. A node cuts its first checkpoint about five minutes after its first activity. This is not a refusal and not an absence.
refusal
The node signed a "no" over this exact request, with a reason. A signed refusal is an answer: the node is up, holds its key, and chose not to disclose. It says nothing bad about the node.
absence
Nothing came back: the node was offline, could not be reached, or did not answer in time. The saved file says why. An absence says nothing about the node's records.
no_announced_key
A reply came back, but the reporter's host had learned no key for the node, so there was nothing to check it against.
not_evidence
A reply came back that is neither a signed answer that checks out nor a signed refusal. The saved file says why.

Each node also has a NODE line: discloses: ... (the questions it answered with a checked signed answer), joined, no checkpoint yet, or joined, discloses nothing.

Why there is no score

Each result is a fact about one exchange on one day: what was asked, what came back, and how it checked. Adding those up into a number per node would claim more than the records say. An absence can be the reporter's own path to the node; a refusal is a node using its policy. So the page has no score, no ranking and no table of nodes by result. Nodes are listed by node id, which is a key, so the order means nothing. The only numbers about nodes are counts for one day, and each says how many nodes it is out of: for example "2 of 3 listed nodes".

How to join and how to leave

Join: run a mesh node with the capsules plugin, then open a pull request that adds one file, nodes/<node_id>.json, to the commitment list repository (its nodes/README.md lists the fields). The list's check must pass. From the next daily run the reporter asks your node. While the network is in its lab stage, only known operators are listed.

Leave: open a pull request that deletes your file and adds a leave mark, nodes/left/<node_id>.json, with the day it merges. From the next run the reporter stops asking your node, and this page lists it as left on that day. Days already reported stay as they are: a report records what was asked and what came back, and is never rewritten.

The list is discovery, not evidence: an entry says how to ask a node, and the answers are the evidence.

Checking an answer yourself

Not yet available. There is no command yet that re-checks one saved answer offline on a fresh machine, and this page will not show one until it works.

Why: a signed answer is bound to the exact bytes of the request it answers (a SHA-256 digest of them). Before sending, the reporter's plugin adds its own members to the request: who is asking, the audience, a fresh nonce, a deadline, and the reporter's signature. The reports save the request as the reporter built it (<q>.request.json) and the plugin's reply around the answer (<q>.response.json), but not the exact bytes that were sent, and those cannot be rebuilt (the nonce is random). So the request binding of a saved answer cannot be re-checked from these files alone.

What closing the gap takes: the plugin's tool reply returns the exact bytes it sent, the reporter saves them beside the answer, and a command-line checker for this answer format is published. Until then, each result here is the reporter's own node's check, and the raw files are linked so you can read exactly what came back.
