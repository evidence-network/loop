Loop stats

This site is the evidence network's. It shows, from files in the network's public repository and nothing else: the loop, the steps a node goes through from sealing a record to a new node joining, and where each step stands; five numbers that say how far the loop has come; and every node on the commitment list, day by day, as the daily reporter found it.

New here? Read what the reporter asks and what each result means. Then the loop, the five numbers, the nodes and each day.

The loop

The loop is the network's test harness: one step per fact, each writing a finding with its proof files. The rehearsal run uses demo nodes and test keys; the live run uses the lab nodes. They are drawn side by side and never added together. A step is green only when its finding says PASS and its proof files match; red is FAIL or a finding that does not pass the format check; grey is NOT_CHECKED, a step that could not establish its fact yet. Each step links to its row on the status page, which lists what, why and the issue that owns it.

$loop

Five numbers

Each number is per population, from that population's newest run. A minutes figure runs from the run's start to the end of the step that marks the event, and is shown out of the whole run's length. A number that cannot be measured yet says so, with the milestone it waits for; it is never shown as zero. The status page says which finding each one reads.

What the reporter asks

Once a day, one node on the mesh, the reporter, asks every node on the commitment list the same two questions and saves exactly what came back. Those saved files are kept in a separate repository that is not published. This site shows a scrubbed record of them: per node per day, the result of each question, every attempt, the log size at the checkpoint, and the SHA-256 of the answer, never the answer's bytes.

Each node on this network keeps a book of sealed records about the exchanges it takes part in, and answers evidence requests under its own disclosure policy. Most records are answered only to the other party of that exchange. Two questions are answered to anyone, and they are the only two the reporter asks:

  • checkpoints: the node's signed checkpoints. Each one commits to the size and root of the node's log at that moment. It shows the book exists and keeps growing, without showing any record in it.
  • history_card/1: a signed card derived from the node's whole history: its checkpoints, each with the proof that it extends the one before. Again, no record's contents.

The reporter asks over the mesh, addressed by node id, and signs every request with its own published key, so each node can see who asked. It asks nothing else, and it never asks itself.

What each result means

Each question gets exactly one result per node per day. On the timeline, the first four are answered, a refusal is refused and an absence is absent.

verified
The node answered, and the reporter's own node ran its check on the answer's signature, under the key the node's host announces on the mesh, and on the answer's form, and both held. It means: this node, holding that key, signed this answer to this request. It does not mean the node's records are true or complete, that the node is trustworthy, or that anyone vouches for it. Repeating that check yourself, offline, is not possible yet; see checking an answer yourself.
no_checkpoint_yet
The node signed a coverage_unsatisfiable answer: it has not cut its first checkpoint yet. A node cuts its first checkpoint about five minutes after its first activity. This is not a refusal and not an absence.
refusal
The node signed a "no" over this exact request, with a reason. A signed refusal is an answer: the node is up, holds its key, and chose not to disclose. It says nothing bad about the node.
absence
Nothing came back: the node was offline, could not be reached, or did not answer in time. Each attempt says how it ended: unreachable, timeout or absence. An absence says nothing about the node's records.
no_announced_key
A reply came back, but the reporter's host had learned no key for the node, so there was nothing to check it against.
not_evidence
A reply came back that is neither a signed answer that checks out nor a signed refusal.

Each node also has a NODE line: discloses: ... (the questions it answered with a signed answer that held), joined, no checkpoint yet, or joined, discloses nothing.

Why there is no score

Each result is a fact about one exchange on one day: what was asked, what came back, and how the reporter's check came out. Adding those up into a number per node would claim more than the records say. An absence can be the reporter's own path to the node; a refusal is a node using its policy. So the site has no score, no ranking and no table of nodes by result. Nodes are listed by node id, which is a key, so the order means nothing. The only numbers about nodes are counts for one day, and each says how many nodes it is out of: for example "2 of 3 listed nodes".

How to join and how to leave

Join: run a mesh node with the capsules plugin, then open a pull request that adds one file, nodes/<node_id>.json, to the commitment list repository (its nodes/README.md lists the fields). The list's check must pass. From the next daily run the reporter asks your node. While the network is in its lab stage, only known operators are listed.

Leave: open a pull request that deletes your file and adds a leave mark, nodes/left/<node_id>.json, with the day it merges. From the next run the reporter stops asking your node, and this site shows it as left on that day. Days already reported stay as they are: a report records what was asked and what came back, and is never rewritten.

The list is discovery, not evidence: an entry says how to ask a node, and the answers are the evidence.

Checking an answer yourself

Not yet available. There is no command yet that re-checks one saved answer offline on a fresh machine, and this site will not show one until it works.

Why: a signed answer is bound to the exact bytes of the request it answers (a SHA-256 digest of them). Before sending, the reporter's plugin adds its own members to the request: who is asking, the audience, a fresh nonce, a deadline, and the reporter's signature. The reporter saves the request as it built it and the plugin's reply around the answer, but not the exact bytes that were sent, and those cannot be rebuilt (the nonce is random). So the request binding of a saved answer cannot be tested again from the saved files alone.

What closing the gap takes: the plugin's tool reply returns the exact bytes it sent, the reporter saves them beside the answer, and a command-line checker for this answer format is published. Until then, each result here is the reporter's own node's result. The saved files themselves are not published; each day shows the SHA-256 of every settled answer, so a copy of an answer can be matched to the one recorded here.
